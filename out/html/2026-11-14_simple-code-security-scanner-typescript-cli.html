Simple Code Security Scanner (TypeScript CLI)

A minimal clone of Codex‑Security for scanning JavaScript/TypeScript files for insecure patterns

Welcome to another official UVF IT build guide! In this tutorial we’ll craft a tiny command‑line scanner that looks for common insecure code snippets – think hard‑coded secrets, eval usage, and unsafe imports – inspired by OpenAI’s Codex‑Security CLI.

We’ll keep everything on your laptop using Node.js, TypeScript, and SQLite (via better‑sqlite3) – no paid APIs, no cloud services. In ~45 minutes you’ll have a runnable scan command that outputs a JSON report of findings.

Prerequisites & Gotchas

  • You need Node.js 22+ (the real tool requires 22.x, 24.x or 26.x). Older versions will fail to run the TypeScript compiler used here.
  • The clone only searches for three hard‑coded patterns; it is not a full security analysis like the original product.
  • SQLite file is created in the project root; delete scanner.db to reset the history.

Phase 1: Scaffold Project

We start by creating a fresh folder for the scanner and turning it into a Node.js project. The npm init -y command writes a basic package.json so we can later add scripts and dependencies. Then we install TypeScript, ts-node for on‑the‑fly execution, a glob library to locate source files, and better‑sqlite3 for a tiny embedded database.

All of these packages are lightweight and work offline, which keeps the clone simple and reproducible. Finally we generate a tsconfig.json that tells the TypeScript compiler to target modern JavaScript and to place compiled files in a dist folder.

mkdir simple-scanner && cd simple-scanner
npm init -y
npm install typescript ts-node @types/node glob better-sqlite3
npx tsc --init --rootDir src --outDir dist --esModuleInterop true --resolveJsonModule true --target ES2022 --module commonjs

Phase 2: Data Model & DB Init

The scanner needs a place to store each finding so we can query or export later. We use SQLite because it’s a single file, requires no server, and the better-sqlite3 driver gives us synchronous, easy‑to‑read code – perfect for a small CLI tool.

The src/db.ts module opens (or creates) scanner.db in the project root and ensures a findings table exists. The table records the file path, line number, rule identifier, and a short code snippet that triggered the alert. Exported helper functions let other parts of the app insert a finding and retrieve all stored records.

src/db.ts

import Database from 'better-sqlite3';

// Open (or create) the SQLite file in the project root
const db = new Database('scanner.db');

// Ensure the findings table exists – runs on first import
const init = db.prepare(`
  CREATE TABLE IF NOT EXISTS findings (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    file TEXT NOT NULL,
    line INTEGER NOT NULL,
    rule TEXT NOT NULL,
    snippet TEXT NOT NULL,
    scanned_at DATETIME DEFAULT CURRENT_TIMESTAMP
  )
`);
init.run();

/** Insert a new finding into the database */
export function addFinding(params: {
  file: string;
  line: number;
  rule: string;
  snippet: string;
}) {
  const stmt = db.prepare(
    'INSERT INTO findings (file, line, rule, snippet) VALUES (?, ?, ?, ?)'
  );
  stmt.run(params.file, params.line, params.rule, params.snippet);
}

/** Retrieve all findings – useful for the CLI report */
export function getAllFindings() {
  const stmt = db.prepare('SELECT * FROM findings ORDER BY scanned_at DESC');
  return stmt.all();
}

Phase 3: Core Scanning Logic (API/UI)

In this phase we build the heart of the scanner: a tiny rule engine that walks a directory, reads JavaScript/TypeScript files, and looks for insecure patterns. When a pattern matches we persist a record in SQLite for later queries and also keep it in memory so the CLI can emit a JSON report. The three starter rules catch obvious red flags – use of eval, assignment to innerHTML, and hard‑coded passwords – which are easy to extend later.

We use the glob package to recursively locate *.js and *.ts files, then apply each rule’s regular expression to the file contents. Findings are stored with file path, line number, rule identifier, and a short snippet. All database interactions are wrapped in a tiny helper that creates the findings table on first run.

src/scanner.ts

import * as fs from 'fs';
import * as path from 'path';
import glob from 'glob';
import sqlite3 from 'sqlite3';
import { open } from 'sqlite';

interface Rule {
  id: string;
  description: string;
  regex: RegExp;
}

const rules: Rule[] = [
  { id: 'eval-usage', description: 'Use of eval()', regex: /eval\s*\(/ },
  { id: 'innerhtml-assignment', description: 'Assignment to innerHTML', regex: /\.innerHTML\s*=/ },
  { id: 'hardcoded-password', description: 'Hard‑coded password string', regex: /['"](?:pwd|password)['"]\s*[:=]\s*['"][^'"\n]+['"]/i }
];

async function getDb() {
  const db = await open({ filename: 'scanner.db', driver: sqlite3.Database });
  await db.exec('CREATE TABLE IF NOT EXISTS findings (id INTEGER PRIMARY KEY AUTOINCREMENT, file TEXT, line INTEGER, rule TEXT, snippet TEXT)');
  return db;
}

export async function runScan(rootDir: string) {
  const db = await getDb();
  const pattern = '**/*.{js,ts}';
  const files = glob.sync(pattern, { cwd: rootDir, absolute: true, nodir: true });
  const findings: any[] = [];
  for (const file of files) {
    const content = fs.readFileSync(file, 'utf8');
    const lines = content.split(/\r?\n/);
    lines.forEach((line, idx) => {
      for (const rule of rules) {
        if (rule.regex.test(line)) {
          const record = { file: path.relative(rootDir, file), line: idx + 1, rule: rule.id, snippet: line.trim() };
          findings.push(record);
          db.run('INSERT INTO findings (file, line, rule, snippet) VALUES (?,?,?,?)', [record.file, record.line, record.rule, record.snippet]);
        }
      }
    });
  }
  await db.close();
  return findings;
}

Phase 4: CLI Entrypoint & Run Locally

Now we expose a friendly command‑line interface so developers can scan any folder with a single command. Using commander we define a scan sub‑command that accepts a directory path, invokes the scanner, and prints a nicely formatted JSON payload to stdout. This makes the tool scriptable and easy to integrate into CI pipelines.

The CLI simply forwards the directory argument to runScan and awaits the result. Errors are caught and displayed, ensuring the user always gets a clear exit status.

src/cli.ts

#!/usr/bin/env node
import { Command } from 'commander';
import { runScan } from './scanner';

const program = new Command();
program
  .name('uvf-scanner')
  .description('Minimal security scanner for JS/TS projects')
  .version('0.1.0');

program
  .command('scan <dir>')
  .description('Scan a directory for insecure patterns')
  .action(async (dir: string) => {
    try {
      const findings = await runScan(dir);
      console.log(JSON.stringify({ findings }, null, 2));
    } catch (err) {
      console.error('Scan failed:', err);
      process.exit(1);
    }
  });

program.parse(process.argv);

Phase 5: Verify & Extend

With the scanner wired up, we can now test it against a tiny sample repository. We'll create a folder containing a file that deliberately uses eval so we can see a finding appear in the JSON output. Once the basic flow works, you can extend the rule set by adding more regex objects to rules or output the data in SARIF or CSV formats for tooling compatibility.

Running the CLI is as simple as invoking npx ts-node src/cli.ts scan ./sample-repo. The pipe to jq helps you inspect a particular finding, confirming that the SQLite table was also populated on the first run.

# Create a sample repo with a vulnerable file
mkdir -p sample-repo && cat > sample-repo/vuln.ts <<'EOF'
// Sample vulnerable code
const userInput = "alert('hi')";
eval(userInput);
const el = document.getElementById('root');
el.innerHTML = '<p>hello</p>';
const password = "secretPwd";
EOF

# Run the scanner and pretty‑print the JSON report
npx ts-node src/cli.ts scan ./sample-repo | jq '.'
