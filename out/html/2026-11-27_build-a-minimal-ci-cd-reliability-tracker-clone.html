Build a Minimal CI/CD Reliability Tracker Clone

A beginner-friendly guide to a lightweight OpenSRE-inspired app

Welcome to another official UVF IT tutorial! In this guide we’ll craft a tiny reliability‑tracker that mimics the core idea of OpenSRE – ingesting a CI failure payload, storing it, and exposing a simple dashboard.

You’ll finish a working prototype in about 45 minutes using only Python, FastAPI, and SQLite – all free and locally hosted.

Before You Start

  • You need Python 3.10+ and git installed; older versions may miss type hints used in the examples.
  • The real OpenSRE ships a sophisticated agent, model integration and authentication – our clone stores raw JSON and shows a static table, which is fine for learning but not production‑ready.
  • Running the FastAPI server on port 8000 may conflict with other local services; adjust the port if needed.

Phase 1: Scaffold the Project

Create a fresh folder for the clone, spin up a virtual environment, and install FastAPI together with an async SQLite driver. This gives us a clean, isolated workspace and the core libraries we’ll use to serve HTTP requests and talk to the database.

We’ll also add Uvicorn, a lightweight ASGI server, so we can run the API locally with a single command. All of these steps are one‑liners you can copy‑paste into a terminal.

mkdir ci_tracker_clone && cd ci_tracker_clone
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install fastapi aiosqlite uvicorn

Phase 2: Define the Data Model

We’ll store each CI failure as a JSON blob, a timestamp, and a short title. Using aiosqlite lets us run async queries that play nicely with FastAPI’s async nature.

The file app/models.py will contain a tiny helper class that creates the table on first run and provides add_failure and list_failures functions for later phases.

app/models.py

import aiosqlite
from datetime import datetime

DB_PATH = "tracker.db"

CREATE_TABLE = """
CREATE TABLE IF NOT EXISTS failures (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    payload TEXT NOT NULL,
    ts TEXT NOT NULL
);
"""

async def init_db():
    async with aiosqlite.connect(DB_PATH) as db:
        await db.executescript(CREATE_TABLE)
        await db.commit()

async def add_failure(title: str, payload: str):
    ts = datetime.utcnow().isoformat()
    async with aiosqlite.connect(DB_PATH) as db:
        await db.execute(
            "INSERT INTO failures (title, payload, ts) VALUES (?, ?, ?)",
            (title, payload, ts),
        )
        await db.commit()

async def list_failures():
    async with aiosqlite.connect(DB_PATH) as db:
        async with db.execute("SELECT id, title, ts FROM failures ORDER BY ts DESC") as cursor:
            rows = await cursor.fetchall()
    return [{"id": r[0], "title": r[1], "timestamp": r[2]} for r in rows]

Phase 3: Build the API & UI

In this step we create a tiny FastAPI service that will receive CI failure payloads and store them in memory. A POST endpoint /payload accepts JSON from any CI system, extracts a few useful fields, and appends them to a global list. We also add a GET route / that renders a simple HTML page showing all stored failures in a table. Keeping everything in one file makes the clone easy to understand and run.

We use Jinja2 templates built‑in to FastAPI for the dashboard, so no separate front‑end build step is required. The in‑memory store is fine for a demo; later you can swap it for SQLite or a real database.

app/main.py

from fastapi import FastAPI, Request
from fastapi.responses import HTMLResponse
from fastapi.templating import Jinja2Templates
from pydantic import BaseModel

app = FastAPI()
templates = Jinja2Templates(directory="templates")

# In‑memory store for received failures
failures = []

class Payload(BaseModel):
    job_name: str
    build_id: int
    status: str
    message: str | None = None

@app.post("/payload")
async def receive_payload(payload: Payload):
    failures.append(payload.dict())
    return {"status": "saved"}

@app.get("/", response_class=HTMLResponse)
async def dashboard(request: Request):
    return templates.TemplateResponse("dashboard.html", {"request": request, "failures": failures})

Phase 4: Run Locally

Now that the API and UI are ready, we launch the development server with Uvicorn. The --reload flag watches for file changes, so you can edit the code and see updates instantly. Once the server is up, open your browser to the address shown to view the dashboard.

If you see an empty table, that just means no payloads have been posted yet – that’s expected for the first run.

uvicorn app.main:app --reload --port 8000
5

Phase 5: Verify & Extend

With the server running, we simulate a CI failure by sending a JSON payload via curl. After the POST returns, refresh the browser; the new entry should appear in the table. This confirms the end‑to‑end flow works.

To experiment further, try adding a query parameter like ?status=failed to filter rows, or modify the Payload model to store the full JSON for later analysis. Those small tweaks illustrate how the clone can grow without much effort.

curl -X POST http://127.0.0.1:8000/payload \
  -H "Content-Type: application/json" \
  -d '{"job_name":"build-42","build_id":42,"status":"failed","message":"Tests failed"}'
