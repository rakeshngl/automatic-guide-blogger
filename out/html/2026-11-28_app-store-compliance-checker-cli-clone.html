App Store Compliance Checker CLI Clone

A minimal command‑line tool to flag common iOS/Android submission issues

Welcome to another official UVF IT build where we craft a tiny yet functional clone of the App Store Compliance Playbook. In just ~45 minutes you’ll have a local CLI that scans a project’s manifest files for red‑flags similar to the original tool.

We’ll use plain Python 3 with the standard library only, store rules in a tiny SQLite DB, and run everything locally – no paid APIs required.

Before you start

  • Make sure Python 3.9+ is installed and sqlite3 is available (bundled with Python).
  • The clone only checks Info.plist (iOS) and AndroidManifest.xml (Android) for a handful of rules – the real project covers many more edge cases.
  • Running on Windows may need git bash or WSL for the shebang line to work.

Phase 1: Scaffold the project

Create a new folder for the clone and initialise a Python virtual environment so dependencies stay isolated. Inside the folder we lay out a minimal structure: a src package for code, a rules folder for the SQLite schema, and a cli.py entry point that will drive the tool.

The virtual environment also gives us a convenient place to store the executable shebang, making the CLI runnable with ./cli.py after we make it executable. This scaffold mirrors the original project's layout but stays lightweight.

mkdir app-compliance-clone
cd app-compliance-clone
python3 -m venv .venv
source .venv/bin/activate
mkdir -p src/rules
touch src/__init__.py src/cli.py rules/init.sql
2

Phase 2: Load compliance rules into SQLite

We store each rule as a row containing an identifier, the target platform, an XPath expression to locate the element in a manifest, and a short description of the violation. SQLite is perfect here because it requires no external server and ships with Python.

The rules/init.sql script creates the rules table and seeds it with a few representative checks – for example, ensuring iOS apps have a UIBackgroundModes entry or Android apps declare the INTERNET permission. Running this script will produce a rules.db file that the CLI can query at runtime.

rules/init.sql

-- Create the rules table
CREATE TABLE IF NOT EXISTS rules (
    id INTEGER PRIMARY KEY,
    platform TEXT NOT NULL,   -- 'ios' or 'android'
    xpath TEXT NOT NULL,      -- simple XPath to evaluate
    description TEXT NOT NULL
);

-- Seed with a few sample rules
INSERT INTO rules (platform, xpath, description) VALUES
('ios', '/plist/dict/key[text()="UIBackgroundModes"]', 'iOS apps should declare background modes when needed'),
('android', '/manifest/uses-permission[@android:name="android.permission.INTERNET"]', 'Android apps must request INTERNET permission');
3

Phase 3: CLI parses manifests and checks rules

In this step we wire up a tiny command‑line interface using the click library. The CLI accepts a path to an iOS .plist or Android AndroidManifest.xml file and will load our rule set from the SQLite database we created earlier. We then parse the manifest with xml.etree.ElementTree (or plistlib for iOS) and compare the extracted values against each rule, printing a warning when a rule is violated. Keeping everything in one file makes it easy to iterate and test locally.

cli.py

import click, sqlite3, sys, os
import xml.etree.ElementTree as ET
import plistlib

DB_PATH = os.path.join(os.path.dirname(__file__), 'rules.db')

def load_rules():
    conn = sqlite3.connect(DB_PATH)
    cur = conn.cursor()
    cur.execute('SELECT key, expected FROM rule')
    rules = {row[0]: row[1] for row in cur.fetchall()}
    conn.close()
    return rules

def parse_android(manifest_path):
    tree = ET.parse(manifest_path)
    root = tree.getroot()
    data = {}
    for elem in root.iter():
        for k, v in elem.attrib.items():
            data[k] = v
    return data

def parse_ios(plist_path):
    with open(plist_path, 'rb') as f:
        return plistlib.load(f)

@click.command()
@click.argument('manifest_path', type=click.Path(exists=True))
def main(manifest_path):
    """Check a mobile app manifest against stored compliance rules."""
    rules = load_rules()
    if manifest_path.lower().endswith('.xml'):
        values = parse_android(manifest_path)
    else:
        values = parse_ios(manifest_path)
    for key, expected in rules.items():
        actual = values.get(key)
        if actual != expected:
            click.secho(f"⚠  {key}: expected '{expected}', got '{actual}'", fg='yellow')
    click.secho('✅ Check complete', fg='green')

if __name__ == '__main__':
    sys.exit(main())

Phase 4: Initialise DB and run locally

Now we create the SQLite database that stores our compliance rules and make the CLI executable. The init script creates a rule table and inserts a couple of sample rules – for example, requiring a minimum iOS version and a specific Android permission. After the DB is ready we give cli.py execute permission and run a quick test against a sample manifest.

#!/usr/bin/env bash
# Initialise SQLite DB
DB_FILE=$(dirname "$0")/rules.db
sqlite3 "$DB_FILE" <<SQL
DROP TABLE IF EXISTS rule;
CREATE TABLE rule (key TEXT PRIMARY KEY, expected TEXT NOT NULL);
INSERT INTO rule (key, expected) VALUES ('minimumOSVersion', '13.0');
INSERT INTO rule (key, expected) VALUES ('android.permission.INTERNET', 'required');
SQL

# Make CLI executable
chmod +x cli.py

# Run a quick sanity check (assumes sample manifests exist)
./cli.py sample/AndroidManifest.xml || true

Phase 5: Verify and extend

With the database and CLI in place we verify that the tool behaves as expected. Run the CLI on a sample manifest and look for the warning lines that indicate rule mismatches; the final green line confirms the process finished. From here you can easily add more rules, support JSON manifests, or even expose a --json flag to output machine‑readable results.

#!/usr/bin/env bash
# Verify output of the CLI against a known bad manifest
./cli.py sample/AndroidManifest.xml >output.txt
cat output.txt
# Expect at least one line starting with the warning symbol
if grep -q '^⚠' output.txt; then
  echo "Warnings detected as expected"
else
  echo "No warnings – check your rules or manifest"
fi
# Extend: add a new rule for iOS bundle identifier
sqlite3 $(dirname "$0")/rules.db "INSERT OR REPLACE INTO rule (key, expected) VALUES ('CFBundleIdentifier', 'com.example.app');"
